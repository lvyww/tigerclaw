# Windows ARM64 Overlay latency measurement — 2026-09-08

## Finding

The native Overlay has a reproducible pre-render latency penalty. In the
matched-input confirmation, publish-to-parsed-state median is 24.394 ms native
versus 8.506 ms WPF. Removing only the native cross-poll matching-snapshot gate
in a separate diagnostic source copy reduces that median to 9.755 ms.
This supports prioritizing publication/read synchronization over replacing the
graphics backend. It does not prove equal end-to-end visible latency.

All tests were isolated. No Core, TSF, Hook, configuration or deployed Overlay
was changed. All test children exited. The deployed ARM64 Overlay still hashes
to `a3bf5593c79909f843c1cb73740e5b117a5cd8dcf9145ccebfc99c1302565916`.

## Matched fixed-input confirmation

Each row has two rounds of 1,000 measured updates, with 50 warm-ups per round.
WPF/native order reverses in round two. The diagnostic control runs afterwards.
Version 2 of the driver resets payload content and pacing RNG per group so the
same workload has exactly matching JSON across implementations. Writes retain
the production legacy sequence-before-payload order.

**Publish start to parsed state available (ms):**

| Implementation | P50 | P95 | P99 |
| --- | ---: | ---: | ---: |
| WPF .NET Framework 4.8 ARM64 | 8.506 | 15.120 | 15.919 |
| Native C++ ARM64, deployed algorithm | 24.394 | 29.839 | 31.181 |
| Native, unsafe single-poll diagnostic | 9.755 | 14.134 | 14.789 |

Native baseline's read-to-UI queue P95 is only 0.113 ms (WPF 1.696 ms), so
UI-message dispatch is not the main measured source of the native penalty.
Removing the gate reduces native read median by 14.639 ms. A separate 100-call
`WaitForSingleObject(event, 5)` probe on this machine measured median 15.622 ms,
P95 17.821 ms (range 6.769–19.104 ms). The configured 5 ms is not the actual
observed waiting period. No timeBeginPeriod or system timer setting was changed.

## Four-workload baseline

Two rounds, 1,000 retained updates per implementation/scenario/round: 16,000
updates total. This first driver revision used a global sequence-derived
hexadecimal code, so text values and pacing RNG positions were not byte-identical
between groups; lengths and workload structure matched. The stricter 6,000-update
confirmation/control above addresses that limitation for the main finding.

**Publish start to parsed state available (ms):**

| Workload | WPF P50 | Native P50 | WPF P95 | Native P95 |
| --- | ---: | ---: | ---: | ---: |
| Fixed code length | 8.143 | 23.649 | 15.243 | 29.628 |
| Changing width | 6.267 | 23.634 | 15.439 | 29.447 |
| Vertical | 10.806 | 23.948 | 14.813 | 29.784 |
| Long sentence candidates | 10.831 | 23.133 | 14.765 | 29.596 |

End-of-group working set samples are 329.0–348.3 MiB WPF versus 25.0–28.4 MiB
native; private commit is 280.6–299.4 MiB versus 9.0–12.6 MiB. These are warmed,
sound-disabled synthetic workloads, not idle-process or user's live memory.
CPU cost is workload-dependent: native is not uniformly better. In the long
sentence stress case, total child CPU averages approximately 6.4–7.1 ms/update
native versus 3.6–4.5 ms/update WPF, including warm-ups and background work.
Screen-bound clipping differs in this stress case, so this is not a normalized
graphics-only benchmark.

### Baseline limits

- There are 22,000 retained acknowledgements across baseline and confirmation;
  no acknowledgement timed out. This one-outstanding-state protocol does not
  test burst/coalescing loss, keyboard-to-screen latency, or real typing.
- `ui -> done` is not an equivalent rendering endpoint: native completes its
  synchronous UpdateLayeredWindow call; WPF still has deferred rendering. No
  claim about actual presentation/photon latency is made. Frame capture or
  high-speed video, plus a real Core/frontend trace, remains a separate test.
- The single-poll build is unsafe with the legacy publication contract. It is
  an experimental ablation, not a deployable fix. The baseline two-poll heuristic
  itself reduces torn reads but is not an atomic consistency guarantee either.
- Next: provide reliable snapshot publication and notification so native need
  not wait another polling cycle. Preserve old-Core compatibility and test torn
  writes, rapid updates, reconnects and latest-state delivery before deployment.
- Only after that, profile/reuse drawing surfaces and text-layout resources;
  this experiment does not establish that switching to GPU rendering is needed.
