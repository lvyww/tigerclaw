# 全拼逐键延迟诊断（2026-09-22）

本文件记录最初分析和隔离测量，当时未替换运行程序或修改用户配置。
后续实现与验收见 [性能改造报告](../../docs/PINYIN_PERFORMANCE_20260922.md)。

## 测量口径

本机 Windows ARM64，Native AOT 独立探针调用与当前 Core 相同的 Pinyin 源码及
桌面测试版资源。万象 2,202,473 词条、三阶 Beam 200 / Top50、完整 Q8 五阶；
默认简拼/拼写兼容开启，错拼/模糊音关闭。模型评分包装器只额外计数调用次数。

8 组固定输入逐字追加：shiyixia、nihaoma、changyongzi、yaoyouhuahaojiu、
jintianxiawuwomenyiqiquchifan、woxiangceshiyixiapinyinshurufa、nh、windowsbanben。
每组解码器 Reset，组内复用增量搜索；运行三轮，共 345 个按键，热态统计使用
后两轮的 230 个按键。每轮等上一个按键计算完成，不模拟真实快速连打。

测量包含三阶搜索、五阶重排、中文菜单、英文/表情及再次构建菜单；不包含
Core Task/锁等待、纠正学习保留搜索、TSF IPC、真实窗口绘制或输入应用接受。
探针只读生产资源，未向实际输入上下文注入测试按键。资源加载是新进程加载，
不保证 OS 文件缓存为空。首选文本可复现，不据此宣称全量准确率不变。

## 实测结果

| 热态阶段 | 中位数 ms | P95 ms | 最大 ms |
|---|---:|---:|---:|
| 三阶搜索 | 4.898 | 134.540 | 344.825 |
| 五阶重排 | 0.227 | 0.574 | 0.882 |
| 中文菜单 | 0.289 | 2.571 | 5.929 |
| 英文/表情及再次构建菜单 | 0.279 | 2.330 | 7.508 |
| 上述总计算 | 6.599 | 135.805 | 350.712 |

搜索占累计测量时间的 95.0%。230 次中有 55 次超过 50 ms，31 次超过 100 ms。
多数按键很快，但拼音未打完时会出现明显长尾：

| raw | 两轮搜索耗时 ms | 每次 LogProbability 调用 | 每键探针线程分配 |
|---|---:|---:|---:|
| changy | 344.825 / 266.537 | 2,128,963 | 135.2 MB |
| woxiangc | 268.791 / 258.308 | 2,048,712 | 130.8 MB |
| changyongz | 237.659 / 176.667 | 1,340,624 | 94.8 MB |
| shiy | 134.930 / 105.865 | 898,796 | 67.3 MB |

调用数包含托管缓存命中，不等于同样次数的原生 KenLM 查询；分配数字包含本按键
测量的各阶段，不能全部归因于单一数组。新进程资源加载 15.892 秒，首次 `s`
解码 7.285 秒（主要还包含懒初始化拼写索引）；这与热态逐键问题分开处理。
运行时一次观察 Core 工作集约 6,526 MiB、Private Bytes 约 6,677 MiB。
这是进程整体快照，未拆分词库、GC 堆及模型页，不能将这些数字等同于词表大小。

## 代码及进一步归因

另一个隔离副本加阶段计时，确认上述慢键时间在 DecodeCore 主搜索；并未进入
末音节 Completions 补全分支。其热态 115 个按键首选与基线一致。阶段探针的
绝对时间受二次运行环境等影响明显，不能与基线混合统计；这里只用于判断分支。

1. `Decoder.Decode` 先尝试精确全拼，未完成时进入通用简拼搜索。`sh`、`shiy`、
   `changy` 等中间状态形成大量简拼匹配。`DecodeCore` 对词条×语言模型上下文
   调用 LogProbability，每组还创建 `double[字数]`，然后才用目标桶分数下界剪枝。
   Kenlm.LogProbability 每次进行三个字符串到 token ID 的字典查询及三元组缓存查询；
   缓存达到 262144 条时整表 Clear。以上是重复计算和分配的主要优化入口。
2. 增量模式扫描起点为 `oldLength + 1 - MaximumLength`。万象最长 code 为 62，
   常见短句每键仍从头枚举词条边，枚举完成后才过滤 `edge.End <= oldLength`。
   状态复用已经存在，但拼写匹配/边枚举没有充分复用。
3. Core 每次按键 Task.Run，旧工作取消；Decoder 捕获取消后 Reset 全部缓存。
   高频连续输入可能额外损失增量复用。补全 Walk/排序内部没有取消检查，Core
   后台需要等它退出才能释放 decode gate。此项是代码风险，未量出实际排队延迟。
4. ApplyFullPinyin -> PinyinSession.Apply 会重建菜单，随后 ApplyPinyinExtras ->
   SetExtras 再重建一次；均在引擎锁内。热态平均两次共约 1.41 ms，可作为低风险整理，
   但单独修改不足以消除 100～350 ms 搜索长尾。
5. Completions 是递归 Walk 子树、过滤、排序再 Take(2000)。独立调用 `s`/`y`
   耗时约 76 ms、分配约 93 MB；`shi` 即使结果为零也耗时约 17 ms。默认简拼模式
   下它不是本批最慢样例的原因，但确有低效遍历，尤其需要覆盖关闭简拼等配置。
6. 当前延时显示候选为空，配置 getter 实际为 0；Native Overlay 使用快照事件唤醒，
   fallback 等待为 5 ms，代码不支持将 100 ms 搜索停顿归因于固定 UI 轮询。
   用户开着 200 ms 候选窗动效，这是几何动画时长，不等于每键固定延迟 200 ms；
   实际视觉开销还需窗口测量。

## 建议实施顺序与验收

1. 优先优化简拼搜索：复用拼写匹配图/只枚举受新键影响的边；词条预存整数 token ID；
   消除每词条×上下文的临时 increments 数组；缓存可共享的词内评分；在明确的
   分数上界下提前剪枝。先保证候选及分数一致，再讨论任何会损失召回率的裁剪。
2. 完善连续输入调度：单个最新代工作器合并旧任务，取消检查进入热循环；只保留
   已完整计算、仍合法的历史状态，不能发布旧代结果。不能以复用部分取消状态换速度。
3. 菜单合并为一次构建，准备工作尽量移出引擎锁，发布时继续校验代际和菜单 token。
4. 冷加载及内存独立改造：流式读取 token 数据、减少中间对象和重复字符串、紧凑
   词库索引；资源预热时完成拼写索引，避免首次按键承担懒初始化。
5. 补全改用按音节/最后音节前缀的直接索引，避免扫描大量不符合补全条件的长词。
   保留现有按频率/编码/文本的次序、Top2000 边界及合法切分规则。
6. 动效可作关闭/缩短的对照试验；五阶重排目前优先级低，当前数据不支持先减模型
   或减少 Top50 来解决热态卡顿。

建议目标：先使同一热态语料逐键计算 P95 低于 30 ms、消除 >100 ms 停顿；
目标尚未实现，不能当作承诺。先用冻结 Top50/分数和前缀/简拼/锁定/学习测试确认
语义一致，再测真实 30/60/100 ms 按键间隔、TSF IPC、候选首帧及掉帧。整体响应
以真实应用端到端数据为准，不用离线均值替代。
